At a glance I chose a Next.js App Router frontend and an asynchronous FastAPI backend for this platform. The data layer relies on Postgres and a private Supabase Storage bucket, all accessed securely via backend routes. Because transcription of long audio can take several minutes, I designed a background worker to handle the provider interactions asynchronously. This keeps the web server free to serve API requests quickly.

The browser requests a signed upload URL from the backend.
The browser uploads the audio file directly to Supabase via XMLHttpRequest.
The backend confirms the file exists and marks the job as queued.
The background worker creates a Gnani Batch STT job and commits its ID.
The background worker starts the Gnani job.
The background worker polls Gnani every 10 s until the job is completed.
The background worker fetches the transcript and deletes the audio object.
The background worker calls Gemini to summarize the transcript.

Upload flow I designed the upload flow to bypass the strict payload size limits enforced by Vercel and Render. The audio file never passes through our backend servers. Instead, the browser initiates the process by calling /api/jobs/initiate. The backend validates the request and issues a Supabase signed URL valid for 10 minutes. The browser then performs a raw PUT request directly to the storage bucket using XMLHttpRequest, which allows the frontend to display accurate byte-level progress. Once the upload finishes, the browser calls /api/jobs/{id}/complete. I added a step here where the backend actively verifies the object's existence using the Storage LIST API before queuing the job. I chose the LIST API because the standard HEAD request occasionally gave false positives. This decoupled approach ensures our backend only handles lightweight JSON URLs and metadata, completely avoiding memory pressure from large audio files. If validation fails — file too large, unsupported format, or daily cap reached — the backend returns a stable error code and the frontend shows a friendly message before any upload attempt.

Where files and data live Audio files live temporarily in a private Supabase Storage bucket. I explicitly configured the system to delete these files immediately after the transcript is securely stored in the database. This decision protects user privacy and conserves our 1 GB free-tier storage quota. For structured data, I chose a Postgres database hosted on Supabase, which the backend connects to via an async session pooler. This database contains a single uploads table that tracks the entire state machine, storing job metadata, the raw unpunctuated transcripts, and the final LLM summaries. I chose not to store LLM-rewritten transcripts; we always display the raw ASR output. All access to the database and storage bucket uses service-role keys. I kept all secrets strictly within environment variables on the backend, ensuring that no sensitive credentials or keys are ever exposed to the frontend or committed to the repository.

Long audio handling I chose the Gnani Batch STT API specifically to handle long audio files, bypassing the strict limitations of their standard REST endpoint. When a job reaches the worker, the backend generates a 3-hour signed download URL for the storage object and passes it to the Gnani cloud_storage source. Gnani fetches the file directly from Supabase, meaning our backend never has to download or process the audio in memory. For the summarization phase, I noticed that Gemini has token limits. I solved this by splitting any transcript longer than 60,000 characters into smaller 30,000-character chunks. The llm.py service summarizes each chunk individually and then performs a final map-reduce step to merge these section summaries into one coherent document. This guarantees that even multi-hour recordings are summarized successfully without dropping information or timing out the LLM provider.

Sync vs background I chose an asynchronous background worker over synchronous HTTP requests because transcription takes about 0.13x the audio duration. A 10-minute file would block a request for over a minute, leading to inevitable timeouts. I built the worker as a single asyncio task running directly inside the FastAPI process, controlled by the application lifespan. The worker polls for jobs using a Postgres query with FOR UPDATE SKIP LOCKED. When it claims a row, it sets a 120-second lease in lease_expires_at. This design prevents concurrent workers from picking up the same job, while ensuring that if the process crashes, the lease will naturally expire and another claim will resume the work. The frontend simply polls our /api/jobs/{id} endpoint every 3 seconds to update the UI. This keeps the architecture incredibly simple, avoiding the need for complex message brokers.

Failure handling I designed the failure handling to be highly transparent. I mapped all Gnani API errors into stable internal codes like PROVIDER_RATE_LIMITED and CORRUPT_OR_UNREADABLE_AUDIO, which the UI displays with friendly messages. Because Gnani's /files endpoint returns 429 errors frequently, I implemented an exponential backoff in completed.py that retries up to 8 times before failing. If the worker encounters a 409 conflict when starting a job, it explicitly calls get_job to determine if the job is running or if it failed. If a START_FAILED status occurs, I clear the gnani_job_id so a manual retry will generate a fresh signed URL. I also separated summary failures from transcription failures. If the Gemini call fails, the job still reaches the completed status with summary_status set to failed. The user retains their transcript and can trigger the /api/jobs/{id}/retry-summary endpoint.

Limits and abuse protection I implemented multiple layers of limits to protect our shared API keys. Because this platform has no real authentication, I scoped jobs to an anonymous X-Session-Id generated by the browser. I enforced a strict 50 MB file size limit across the stack: the browser checks it, the /initiate API rejects larger files, and the bucket enforces it at the storage layer. I also added daily limits, specifically capping the number of uploads per session and globally across the platform. These caps are checked in the database before granting an upload URL. I configured the worker with a MAX_CLAIMS limit of 5 to break infinite crash loops, and a 3600-second TRANSCRIBE_TIMEOUT_S to catch jobs that stall on Gnani's servers. Finally, a background sweeper runs every 5 minutes to mark abandoned uploads as failed and clean up timed-out processes.

How it was verified I verified the core logic using a suite of about 150 mocked unit tests and 18 integration tests. The unit tests ensure that state transitions, error mappings, and backoff calculations work correctly. The integration tests run against a real Postgres database in a throwaway schema, proving that the FOR UPDATE SKIP LOCKED query correctly handles concurrent claims and lease expirations. I also wrote live scripts to test the actual Gnani and Supabase APIs. These live runs were crucial because they revealed bugs that the fakes hid. For example, I discovered that Gnani's /files endpoint returns durations as strings, that Supabase's LIST request must be used because HEAD occasionally returns a false positive, and that a missing /storage/v1 prefix was breaking signed URLs. The live tests also forced me to handle HTTP 409 conflicts correctly when starting jobs.

Known limitations I accepted several limitations to ship this quickly on free-tier hosting. The most visible issue is that the Render instance goes to sleep when idle. The worker only runs while the server is awake, though the frontend's 3-second polling keeps it active while a user waits. If the user closes their tab, the job pauses until the next request wakes the server. There is also a small unclosable window: if the worker process crashes after Gnani accepts a job but before we commit the ID to Postgres, we will pay for an orphan transcription. Audio deletion is strictly best-effort; if the Supabase delete call fails, the file remains in the bucket indefinitely. The transcripts lack punctuation, and the system relies entirely on the user to select the correct language since there is no auto-detection. Finally, the session-based authorization provides no real security against a determined actor clearing their local storage. If the delete call fails, no retry mechanism exists for completed jobs, so the file remains in the bucket until manually removed. Additionally, there is no programmatic enforcement of the single-process requirement; running two instances would cause both workers to compete for jobs. The deployment relies on Render being configured with exactly one instance.

Alternatives considered I considered using Gnani's REST API, but rejected it because it rejects audio longer than 30 seconds. Supporting it would have required running ffmpeg to split the file, managing a chunk table, and dealing with mid-word cuts, which was too complex. I considered using webhooks to receive status updates, but rejected them because our free-tier Render instance sleeps and would completely miss the incoming HTTP callbacks. I considered adding Redis and Celery for the background jobs, but rejected them to minimize infrastructure overhead; Postgres was already required, and using it as a queue was simpler. I also considered WebSockets for pushing real-time status updates to the browser. I rejected them because job state changes take seconds to minutes, making 3-second polling with error backoff adequate for our needs and much easier to deploy.

What I would do with more time If I had more time, I would replace the anonymous session IDs with real user accounts and proper authentication. I would deploy the backend to an always-on instance so background jobs never stall, and I would replace the polling worker with Postgres LISTEN and NOTIFY for instant dispatch. For the upload flow, I would implement resumable uploads to support files far larger than 50 MB, and I would add server-side audio validation using ffprobe to reject corrupt files early. On the AI side, I would add a post-processing step to insert punctuation and inverse text normalization, along with speaker diarization and word-level timestamps. Operationally, I would build a scheduled cleanup job to catch and delete orphan files and Gnani jobs, implement structured JSON logging, add per-IP rate limits, and track cost accounting per job.
